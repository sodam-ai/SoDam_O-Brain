# O-Brain — 데이터 모델

> 이 문서는 앱에서 다루는 핵심 데이터의 구조를 정의합니다.
> 개발자가 아니어도 이해할 수 있는 "개념적 ERD"입니다.

---

## 전체 구조

```
[프로젝트(텍스트)] --1:N--> [세션] --1:N--> [기억] --N:N(연결)--> [기억]
                                       |
                                       └--1:1--> [분류(온톨로지)]

  · [연결] = 기억과 기억 사이의 관계선 (영향줌·뒷받침·대체함·모순됨)  ← 이게 지식그래프
  · [분류] = 기억이 속한 주제 태그 (보안·UI·배포 등)
```

> [갱신, 2026-09-01 확인됨] 위 다이어그램은 **개념적 관계**만 나타냄. 실제 구현(`app/src/db.mjs`)에서 [프로젝트]·[분류]는 별도 테이블이 아니라 [세션]/[기억] 안의 **텍스트·스칼라 컬럼**이다(아래 각 섹션 참고). 별도 테이블·정션 테이블이 실재하는 건 [세션]·[기억]·[연결] 3개뿐.

---

## 엔티티 상세

### 프로젝트 (Project)
어떤 작업/저장소(repo)인지. 기억을 묶는 가장 큰 단위.

> [갱신, 2026-09-01 확인됨] 아래는 최초 개념 설계였고, 실제 구현은 더 단순하다: 별도 `project` 테이블이 없고, `session.project`·`memory.project`가 **각각 자유 텍스트 컬럼**(작업 폴더 절대경로 문자열)으로 프로젝트를 나타낸다. `name`·`created_at` 같은 프로젝트 메타데이터는 별도로 저장되지 않는다(필요해지면 Phase 2 이후 검토).

| 필드 | 설명 | 예시 | 필수 |
|------|------|------|------|
| id | 고유 식별자 (자동 생성) | proj_abc123 | O |
| name | 프로젝트 이름 | "O-Brain" | O |
| path | 작업 폴더 경로 | D:\...\O-Brain | X |
| created_at | 만든 날짜 (자동) | 2026-06-20 | O |

### 세션 (Session)
AI와의 한 번의 대화. 언제, 어떤 도구로 했는지.

| 필드 | 설명 | 예시 | 필수 |
|------|------|------|------|
| id | 고유 식별자 (자동) | sess_def456 | O |
| project_id | 어느 프로젝트인지 | proj_abc123 | O |
| tool | 어떤 AI 도구 | "claude-code" / "codex" | O |
| ended_at | 종료 시각 (자동) | 2026-06-20 14:40 | O |
| summary | 세션 한 줄 요약 (AI 생성) | "포트·DB 설정 논의" | X |

> [갱신, 2026-09-01 확인됨] `started_at`은 실제 `app/src/db.mjs`의 `session` 테이블에 구현되지 않아 표에서 제거함(세션은 종료 시점에만 `ended_at`으로 기록됨). 개념 설계 당시 초안에는 있었으나 구현되지 않은 필드.

### 기억 (Memory) — 핵심 엔티티
대화에서 자동으로 뽑은 한 가지 사실. 그래프의 '점(노드)'.

| 필드 | 설명 | 예시 | 필수 |
|------|------|------|------|
| id | 고유 식별자 (자동) | mem_ghi789 | O |
| session_id | 어느 세션에서 나왔는지 | sess_def456 | O |
| type | 기억 유형 | 결정/선호/패턴/지식/제약 | O |
| content | 기억 내용 (시크릿 제거됨) | "테스트 포트는 1601 사용" | O |
| importance | 중요도 ★1~5 | 4 | O |
| confidence | 추출 신뢰도 0~1 (AI추출=낮게 시작, 사용자 확인=1.0) | 0.6 | O |
| source | 출처 (ai / rule / user) — 누가 만든 기억인지 | "ai" | O |
| embedding | 의미검색용 벡터 (자동 생성) | [0.12, -0.03, ...] | O |
| scope | 범위 | "project" / "global" | O |
| access_count | 열어본 횟수 (자동, 그래프 글로우용) | 12 | O |
| last_accessed_at | 마지막 열람 시각 (자동) | 2026-06-20 | X |
| valid_from | 이 기억이 사실이 된 시점 (시간여행용) | 2026-06-20 | O |
| valid_until | 더는 유효하지 않게 된 시점 (null=현재 유효) | null | X |
| invalidated_by | 이 기억을 대체한 기억 id (진화 추적, null 가능) | mem_xyz999 | X |
| created_at | 만든 날짜 (자동) | 2026-06-20 | O |

> **보안 규칙(중요)**: `content`에는 비밀번호·API키·토큰이 **절대 평문으로 저장되지 않는다**. 저장 직전 보안 필터가 자동 제거(마스킹)한다. (근거: agentmemory의 privacy filter 방식 — 확인됨)
>
> **시각화·시간 필드(추가)**: `access_count`=그래프 글로우(자주 본 기억 강조), `importance`+연결수=노드 크기, `valid_from`/`valid_until`/`invalidated_by`=타임라인·시간여행·진화 추적용. (근거: buildautomata 3D viz의 크기·글로우 규칙 + Graphiti/Memento의 temporal 필드 — 확인됨)

### 연결 (Relation) — 지식그래프의 '선(엣지)'
기억과 기억 사이의 관계. 이것이 O-Brain의 차별점.

| 필드 | 설명 | 예시 | 필수 |
|------|------|------|------|
| id | 고유 식별자 (자동) | rel_jkl012 | O |
| from_memory_id | 출발 기억 | mem_ghi789 | O |
| to_memory_id | 도착 기억 | mem_mno345 | O |
| relation_type | 관계 종류 | 영향줌/뒷받침/대체함/모순됨 | O |
| created_at | 만든 날짜 (자동) | 2026-06-20 | O |

> 관계 종류 4종은 memory-bank의 INFLUENCES/SUPPORTS/SUPERSEDES/CONTRADICTS를 일상어로 옮긴 것(확인됨).

### 분류 (Category / 온톨로지)
기억이 속한 주제 태그. 그래프를 묶어서 보거나 필터링할 때 사용.

> [갱신, 2026-09-01 확인됨] 아래는 최초 개념 설계(N:N)였고, 실제 구현(Phase 1 슬라이스, `app/src/classify.mjs` 주석에 명시)은 더 단순하다: 별도 `category` 테이블·정션 테이블이 없고, `memory.category`가 **단일 텍스트 컬럼**이다 — 규칙 기반 자동분류(`classify()`)로 한 기억당 정확히 **하나**의 분류만 부여된다. 다중분류(N:N)는 코드 주석에 이미 "다음 단계"로 명시된 **의도적 Phase 2 계획**이며, 아직 없는 게 결함이 아니라 예정된 확장이다.

| 필드 | 설명 | 예시 | 필수 |
|------|------|------|------|
| id | 고유 식별자 (자동) | cat_pqr678 | O |
| name | 분류 이름 | "보안" / "UI" / "배포" | O |
| created_at | 만든 날짜 (자동) | 2026-06-20 | O |

> **Phase 1 실제 구현**: 기억 ↔ 분류는 **1:1**(한 기억은 정확히 하나의 분류). **Phase 2 계획**: N:N(한 기억이 여러 분류에 속할 수 있고, 한 분류에 여러 기억) — 중간 연결표(memory_category) 도입 예정.

### 관계 요약
- **프로젝트 1개**에 여러 **세션**이 속한다 (1:N, 단 프로젝트는 텍스트 컬럼이지 별도 테이블 아님).
- **세션 1개**에서 여러 **기억**이 나온다 (1:N).
- **기억**은 다른 **기억**과 여러 갈래로 연결된다 — [연결]을 통해 (N:N). → 지식그래프.
- **기억**은 정확히 하나의 **분류**에 속한다 (1:1, Phase 1). N:N 다중분류는 Phase 2 계획.

## 왜 이 구조인가

> 4개 참고 도구(memory-bank·agentmemory·claude-mem)의 공통 뼈대를 1인·로컬·그래프 목적에 맞게 단순화했다.

- **그래프가 1급 시민**: '기억(노드) + 연결(엣지)'을 별도 엔티티로 분리해, 차별점인 지식그래프를 처음부터 자연스럽게 구현(memory-bank 방식). 단순 목록 도구와 갈리는 지점.
- **확장성**: Phase 2의 '관계 자동 추론', Phase 3의 '중복·모순 정리'가 [연결] 테이블 위에서 그대로 확장된다. 뼈대를 안 바꿔도 됨.
- **단순성**: 외부 그래프DB(Neo4j 등)를 쓰지 않고 SQLite 한 파일에 노드·엣지·벡터·전문검색을 모두 담아 의존성 0 유지(agentmemory의 교훈 — 확인됨). Revka의 관리형 Neo4j(Kumiho)는 로컬 목적과 어긋나 배제.
- **검색 통합**: `embedding`(의미검색·sqlite-vec) + `content`(키워드검색·FTS5)를 한 테이블에 두어, 두 검색을 합쳐(하이브리드) 정확도를 높인다.
